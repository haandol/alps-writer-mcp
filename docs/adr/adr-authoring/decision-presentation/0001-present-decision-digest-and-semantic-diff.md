# ADR 0001: ADR 상호작용은 Decision Digest와 semantic diff를 우선 표시

Date: 2026-08-17

## Status

Accepted (2026-08-17)

## Context

AI가 ADR을 작성하거나 수정하면 사용자는 전체 문서에서 현재 결정, 반드시 지켜야 하는 계약과 변경된 근거를 다시 찾아야 한다. ADR 본문은 독립적으로 읽을 수 있는 완전한 기록이어야 하지만, 매 상호작용에서 전체 본문을 반복하면 검토해야 할 정보량이 증가한다.

ADR 본문을 축약하거나 별도 요약 문서를 권위로 만들면 요구사항 계약이나 선택 근거가 손실될 수 있다. 사용자 화면만 현재 질문과 변경에 맞게 압축하고, ADR 본문과 매핑은 기존 권위를 유지해야 한다.

AI는 사용자가 명시하지 않은 전제를 바탕으로 대안을 비교할 수 있다. 전제가 숨겨지면 사용자는 결정의 결론만 보고 왜 그 선택이 합리적인지, 어떤 사실이 틀리면 다시 결정해야 하는지 판단하기 어렵다. 반대로 구현 라이브러리와 튜닝 값 같은 코드 수준 선택까지 ADR에 올리면 ADR의 추상화 수준이 무너진다.

## Decision Drivers

- 사용자는 전체 ADR을 반복해서 읽지 않고 현재 결정, 계약과 결정 전제를 판단할 수 있어야 한다.
- 요구사항 값, 금지 규칙, 실패 보장과 선택 근거는 요약 과정에서 손실되면 안 된다.
- 결정에 영향을 준 전제는 근거와 틀렸을 때의 영향을 함께 보여야 한다.
- 주니어 개발자도 평이한 설명과 적절한 다이어그램으로 결정의 흐름을 이해할 수 있어야 한다.
- 요약 화면과 구현 재량 목록이 ADR 본문과 별도의 영속 권위가 되면 안 된다.

## Decision

ADR 작성, 수정, 문서 리뷰와 동기화의 기본 사용자 화면은 **Decision Digest**와 **semantic diff**를 우선 표시한다.

Decision Digest는 결정 질문, 현재 결정, 요구사항 계약, 결정 전제, 선택 이유와 주요 위험을 평이한 언어로 보여준다. 요구사항 계약은 내용이 있을 때 `필수 보장`, `금지`, `실패 시 보장`으로 묶어 스캔할 수 있게 한다.

ADR 본문은 결정에 영향을 준 **Decision premises**를 Context 아래에 기록할 수 있다. 각 전제는 전제 내용, 근거, 신뢰도와 전제가 틀렸을 때 다시 검토할 결정을 설명한다. 요구사항 값과 규칙은 전제가 아니라 requirement contract에 기록한다. 계약이나 아키텍처 경계를 바꾸는 미확정 전제는 승인 전에 사용자에게 질문하며, 확인되지 않은 상태로 Accepted 결정의 근거처럼 쓰지 않는다.

기존 ADR이 바뀌면 전체 본문보다 Decision, requirement contract, Decision Drivers와 Consequences의 의미 변경을 먼저 보여준다. 전체 ADR, 대안의 상세 비교와 코드 근거는 사용자가 요청하거나 판정에 필요할 때 제공한다. Digest와 diff는 대화 또는 보고 화면이며 별도 권위 문서로 저장하지 않는다.

결정의 흐름, 상태, 시스템 경계나 대안 관계가 문장보다 다이어그램으로 명확하면 근거가 확인된 Mermaid를 사용한다. 다이어그램은 본문을 장식하거나 코드 구조를 복제하지 않고 결정 이해에 필요한 관계만 보여준다.

ADR에 없는 라이브러리, 튜닝 값과 내부 구조 같은 구현 재량은 Decision premises에 기록하지 않는다. 구현 리뷰가 실제 선택값, 근거와 변경 영향을 별도의 일시적 Implementation Choice Ledger로 보여주며, admission gate를 통과하는 선택만 ADR 미결정으로 다시 올린다.

### Requirement contract

#### 필수 보장

- `/adr-new`의 승인 화면은 결정 질문, 현재 결정, 요구사항 계약, Decision premises, 선택 이유, 주요 위험과 재생성 체크를 포함한다.
- 요구사항 계약은 해당 항목이 있을 때 `필수 보장`, `금지`, `실패 시 보장`으로 그룹화한다.
- Decision premise는 전제 내용, 근거, 신뢰도와 전제가 틀렸을 때 다시 검토할 결정을 포함한다.
- 요구사항 값, 허용 상태, 권한과 실패 보장은 Decision premise로 낮추지 않고 requirement contract에 유지한다.
- 계약이나 지속적인 아키텍처 경계에 영향을 주는 미확정 전제는 승인 전에 질문하고 해결한다.
- 결정 흐름, 상태, 시스템 경계나 대안 관계가 문장보다 명확하면 근거가 확인된 Mermaid를 사용한다.
- ADR 수정 경로는 Decision, requirement contract, Decision Drivers와 Consequences의 semantic diff를 승인 전에 보여준다.
- `/adr-review`의 채팅 요약은 중요한 발견을 `결정`, `계약`, `근거`, `위험` 관점으로 압축한다.
- `/adr-sync`의 채팅 요약은 변경된 결정과 계약을 먼저 보여주고 파일·코드 근거는 상세 보고에 유지한다.
- 전체 ADR 본문과 상세 대안은 사용자가 요청하거나 판정에 필요할 때 제공한다.

#### 금지

- Decision Digest나 semantic diff를 별도 영속 문서 또는 새로운 권위로 저장하지 않는다.
- 요약을 위해 요구사항 값, 허용 집합, 금지 전이, 권한, 필수성, 순서, 유일성, 단위와 실패 보장을 생략하지 않는다.
- 구현 라이브러리, 내부 코드 구조, 튜닝 값과 코드에서 복구 가능한 기본값을 Decision premise로 올리지 않는다.
- 근거가 없는 관계를 다이어그램에 추가하거나 이해에 기여하지 않는 장식용 다이어그램을 만들지 않는다.
- 코드 경로, 테스트 파일, PR 또는 커밋 계획을 ADR 본문이나 Decision Digest의 계약으로 올리지 않는다.

#### 실패 시 보장

- semantic diff를 확정할 수 없으면 변경 없음으로 표시하지 않고 확인되지 않은 축을 명시한다.
- Decision premise의 근거나 신뢰도를 확인할 수 없으면 사실로 단정하지 않고 미확정 질문으로 표시한다.
- 요약만으로 계약 완전성을 보장할 수 없으면 전체 ADR 본문과 재생성 체크로 확장한다.

### Alternatives

1. **항상 전체 ADR 본문 표시**
   - 장점: 모든 정보가 한 번에 보인다.
   - 단점: 변경되지 않은 내용까지 반복해서 읽어야 한다.

2. **별도 요약 문서를 ADR마다 저장**
   - 장점: 짧은 문서를 직접 열 수 있다.
   - 단점: ADR 본문과 두 개의 권위가 생겨 서로 드리프트할 수 있다.

3. **영속 ADR은 유지하고 상호작용만 Digest와 semantic diff로 압축**
   - 장점: 권위를 늘리지 않으면서 현재 결정과 변경에 집중할 수 있다.
   - 단점: 각 skill이 일관된 요약 형식을 유지해야 한다.

## Consequences

### Positive

- 사용자는 ADR의 현재 결정과 계약을 먼저 읽고 필요한 상세만 확장할 수 있다.
- 결정이 의존하는 전제와 전제가 틀렸을 때의 영향을 빠르게 확인할 수 있다.
- 주니어 개발자도 평이한 설명과 다이어그램으로 결정의 핵심 흐름을 먼저 이해할 수 있다.
- ADR 변경 검토에서 변경되지 않은 문맥을 다시 읽는 비용이 줄어든다.
- 기존의 single-level read와 current-state 원칙을 유지한다.

### Negative

- 작성, 리뷰와 동기화 skill의 출력 규칙이 늘어난다.
- 작성자는 요구사항, 결정 전제와 구현 재량을 구분해야 한다.
- 잘못 압축한 Digest는 중요한 계약을 가릴 수 있어 회귀 테스트가 필요하다.

### Risks

- 간결화를 이유로 계약을 누락할 수 있다. 재생성 체크와 계약 그룹은 원문 값과 규칙을 그대로 유지해야 한다.
- 구현 재량을 Decision premise로 올리면 ADR이 코드 수준으로 내려갈 수 있다. admission gate와 code-readthrough test로 경계를 지킨다.
- 전제를 많이 나열하면 Digest가 다시 길어진다. 대안 선택을 실제로 바꾸는 전제만 기록한다.
- semantic diff가 단순 문자열 diff로 퇴화할 수 있다. 변경은 문장 위치가 아니라 Decision, 계약, Driver와 Consequence의 의미를 기준으로 분류해야 한다.
