# ADR 0001: ADR 상호작용은 Decision Digest와 semantic diff를 우선 표시

Date: 2026-08-17

## Status

Accepted (2026-09-03)

## Context

AI가 ADR을 작성하거나 수정하면 사용자는 전체 문서에서 현재 결정, 반드시 지켜야 하는 계약과 변경된 근거를 다시 찾아야 한다. ADR 본문은 독립적으로 읽을 수 있는 완전한 기록이어야 하지만, 매 상호작용에서 전체 본문을 반복하면 검토해야 할 정보량이 증가한다.

ADR 본문을 축약하거나 별도 요약 문서를 권위로 만들면 요구사항 계약이나 선택 근거가 손실될 수 있다. 사용자 화면만 현재 질문과 변경에 맞게 압축하고, ADR 본문과 매핑은 기존 권위를 유지해야 한다.

대안 선택이 특정 가정에 의존할 수 있지만, 모든 가정에 별도 section, 근거, 신뢰도와 대안 영향 형식을 요구하면 Context와 Decision Drivers를 반복한다. 결정에 중요한 가정만 기존 ADR 구조 안에서 짧게 드러내야 한다.

ADR은 구현 청사진이 아니라 재생성 계약이다. 코드를 여러 번 다시 만들어도 구현 구조와 이름은 달라질 수 있지만 같은 요구사항을 준수해야 한다. 따라서 각 계약은 구현 리뷰가 독립적으로 대조할 수 있는 한 가지 의무를 표현하고, 충족 여부를 판단할 구현 독립적인 관찰 기준을 함께 제공해야 한다.

문서 리뷰와 동기화 결과가 규칙 ID, 파일 경로와 긴 발견 목록부터 시작하면 해당 ADR을 처음 보는 개발자는 무엇이 바뀌었고 왜 중요한지 파악하기 전에 증거 구조를 먼저 해석해야 한다. 반대로 쉬운 설명을 만든다는 이유로 계약값과 근거를 요약에서 빼면 검토 가능한 보고서가 아니라 해설문이 된다.

시각화도 선택 여부만 모델 판단에 맡기면 여러 ADR의 충돌, 의존 관계, 상태 흐름과 변경 전후 의미가 긴 목록으로 남을 수 있다. 고정 개수의 다이어그램은 단순한 PASS에도 형식 비용을 만들지만, 관계를 독자가 머릿속에서 재구성해야 하는 조건은 명시할 수 있다.

ADR의 각 section을 형식적으로 채우면 결정의 의도보다 Drivers, 계약과 Alternatives 목록이 먼저 보일 수 있다. 반복 대조문, 장식용 영어 명칭, 강제된 번호 구조와 generic bridge가 겹치면 문장은 매끄러워도 어떤 결정이 중요한지 흐려진다. ADR은 독자가 현재 결정과 이유를 빠르게 복원하도록 쓰고, 스타일을 위해 일화나 확신을 만들어서는 안 된다.

## Decision Drivers

- 사용자는 전체 ADR을 반복해서 읽지 않고 현재 결정, 계약과 선택 근거를 판단할 수 있어야 하며, 해당 내용을 처음 보는 주니어 개발자도 결론과 다음 조치를 상세 증거보다 먼저 이해할 수 있어야 한다.
- 요구사항 값, 금지 규칙, 실패 보장과 선택 근거는 요약 과정에서 손실되지 않고 각 계약 행별로 판정 가능해야 한다.
- 관찰 기준은 구현을 고정하지 않으면서 잘못된 결과를 식별할 수 있어야 한다.
- 대안 선택을 바꾸는 가정은 드러나야 하지만 별도 분류 체계를 만들지 않아야 한다.
- 요약 화면은 별도의 영속 권위가 되면 안 되며 관계를 재구성해야 하는 보고서는 근거 있는 Mermaid를 사용해야 한다.

## Decision

ADR 작성, 수정, 문서 리뷰와 동기화의 기본 사용자 화면은 **Decision Digest**와 **semantic diff**를 우선 표시한다.

Decision Digest는 결정 질문과 현재 결정을 먼저 보여주고, 요구사항 계약, 선택 이유와 주요 위험을 평이한 언어로 이어간다. 계약과 근거는 나열 순서보다 판단 중요도와 인과관계에 따라 배치한다. 요구사항 계약은 내용이 있을 때 `필수 보장`, `금지`, `실패 시 보장`, `관찰 가능한 검증 기준`으로 묶는다.

각 요구사항 계약 행은 하나의 독립적으로 검토 가능한 의무만 담는다. `관찰 가능한 검증 기준`은 구현체와 무관하게 어떤 결과를 확인하면 해당 의무의 충족 여부를 판정할 수 있는지 기록한다. 테스트 파일, 명령, 함수, 클래스, 라이브러리와 내부 데이터 표현은 기록하지 않는다.

대안 선택을 실제로 바꾸는 가정이 있으면 Context 또는 관련 Decision Driver에 `가정 — 틀리면 다시 검토할 결정`을 한 줄로 기록한다. 별도 Decision premises section, 신뢰도 등급이나 고정 표는 만들지 않는다. 요구사항 값과 규칙은 requirement contract에 유지하고, 구현 라이브러리와 튜닝 값은 코드 수준에 둔다. 계약이나 지속적인 경계에 영향을 주는 미확정 가정은 승인 전에 질문한다.

기존 ADR이 바뀌면 전체 본문보다 Decision, requirement contract, Decision Drivers와 Consequences의 의미 변경을 먼저 보여준다. 전체 ADR, 대안의 상세 비교와 코드 근거는 사용자가 요청하거나 판정에 필요할 때 제공한다. Digest와 diff는 대화 또는 보고 화면이며 별도 권위 문서로 저장하지 않는다.

`/adr-review`와 `/adr-sync`의 사람용 보고서는 상세 목록보다 먼저 **한눈에 보기**를 제공한다. 한눈에 보기는 결론, 사용자 또는 운영 영향, 필요한 다음 조치와 남은 위험을 평이한 언어로 답한다. 해당 주제를 처음 보는 주니어 개발자를 독자로 가정하고, 피할 수 없는 도메인·기술 용어는 처음 한 번만 짧게 설명한다. 규칙 ID, 경로, 인용과 상세 근거는 전체 보고서에 유지한다.

다음 중 하나라도 있으면 보고서에 근거가 확인된 Mermaid를 포함한다.

- 세 개 이상의 참여자, 단계, 상태 또는 ADR 관계
- 시스템 경계, 의존 관계 또는 ADR 간 충돌
- 상태 전이, 실패, 재시도, rollback 또는 fallback
- 변경 전후 의미를 문장만으로 비교하면 독자가 흐름을 다시 조립해야 하는 경우

요청·이벤트 흐름은 `sequenceDiagram`, 상태는 `stateDiagram-v2`, 분기·의존·충돌은 `flowchart`, 데이터 관계는 `erDiagram`을 우선한다. 가장 작은 유용한 다이어그램을 선택하고, 다이어그램 뒤에 독자가 확인할 핵심을 한 문장으로 적는다. 한두 문장으로 충분한 단일 ADR PASS에는 다이어그램을 생략할 수 있다. 다이어그램은 계약값, 규칙, 근거와 판정을 대체하지 않으며 본문을 장식하거나 코드 구조를 복제하지 않는다.

ADR 본문과 사람용 보고서는 독자, 결정 의도와 근거 상태를 먼저 정한 뒤 쓴다. Context는 실제 문제와 결정 압력을 먼저 설명하고, Decision은 현재 선택과 결과를 직접 말한다. 근거가 있는 causal flow가 설명을 돕는 경우 그 흐름을 사용하되, 일화·측정·결과를 추측해서 만들지 않는다.

사람용 리뷰 리포트는 사용자가 현재 사용하는 언어가 명확하면 그 언어를 사용한다. 별도 언어 신호가 없으면 대상 ADR 본문의 주 언어를 따른다. 여러 ADR을 한 리포트에서 다루면 해당 범위의 주 언어를 사용한다. 번역이 정확도를 낮추는 기술 용어와 고정 artifact anchor는 원문을 유지할 수 있다.

반복 대조문, 한 번만 쓰는 장식용 영어 명칭, 강제된 첫째·둘째·셋째 구조, `핵심은`·`중요한 것은`·`결국` 같은 filler bridge, 인접 prose를 반복하는 표·다이어그램·강조문을 AI-slop 신호로 본다. 신호는 자동 금지어가 아니며 문맥상 자연스럽고 필요한 표현은 남긴다. 관찰, 추론과 제안을 구분하고 근거보다 강한 결론을 쓰지 않는다.

### Requirement contract

#### 필수 보장

- `/adr-new`의 승인 화면은 결정 질문, 현재 결정, 요구사항 계약, 선택 이유, 주요 위험과 재생성 체크를 포함한다.
- ADR 본문과 Decision Digest는 결정 의도와 현재 결정을 세부 목록보다 먼저 설명한다.
- Context는 확인된 문제와 결정 압력에서 시작하고, Decision은 현재 선택과 관찰 결과를 직접 말한다.
- 설명 가능한 causal flow가 있으면 나열보다 그 흐름을 우선하고, 흐름 안에서도 영향이 큰 결정과 계약을 먼저 보여준다.
- 사람용 리뷰 리포트는 명시된 사용자 언어를 우선하고, 없으면 대상 ADR 또는 리뷰 범위의 주 언어를 사용한다.
- 요구사항 계약은 해당 항목이 있을 때 `필수 보장`, `금지`, `실패 시 보장`, `관찰 가능한 검증 기준`으로 그룹화한다.
- 각 요구사항 계약 행은 구현 리뷰가 개별 달성 상태를 부여할 수 있도록 하나의 의무만 표현한다.
- 관찰 가능한 검증 기준은 각 계약의 충족 여부를 판정할 결과를 구현 독립적인 언어로 기록한다.
- 재생성 체크는 구현 구조와 이름이 달라도 모든 계약 행과 관찰 기준을 만족하는 코드를 다시 만들 수 있는지 확인한다.
- 대안 선택을 바꾸는 가정은 Context 또는 관련 Decision Driver에 가정과 틀렸을 때 다시 검토할 결정을 한 줄로 기록한다.
- 요구사항 값, 허용 상태, 권한과 실패 보장은 가정으로 낮추지 않고 requirement contract에 유지한다.
- 계약이나 지속적인 아키텍처 경계에 영향을 주는 미확정 가정은 승인 전에 질문하고 해결한다.
- ADR 수정 경로는 Decision, requirement contract, Decision Drivers와 Consequences의 semantic diff를 승인 전에 보여준다.
- `/adr-review`의 채팅 요약은 중요한 발견을 `결정`, `계약`, `근거`, `위험` 관점으로 압축한다.
- `/adr-sync`의 채팅 요약은 변경된 결정과 계약을 먼저 보여주고 파일·코드 근거는 상세 보고에 유지한다.
- `/adr-review`와 `/adr-sync`의 사람용 보고서는 결론, 영향, 필요한 조치와 남은 위험을 담은 한눈에 보기로 시작한다.
- 사람용 보고서는 해당 주제를 처음 보는 주니어 개발자가 이해할 수 있는 평이한 언어를 사용하고, 피할 수 없는 용어는 처음 한 번만 설명한다.
- 세 개 이상의 참여자·단계·상태·ADR 관계, 시스템 경계, 의존·충돌, 상태 전이 또는 실패·재시도·rollback·fallback이 있으면 가장 작은 유용한 Mermaid를 포함한다.
- 각 Mermaid 뒤에는 독자가 확인할 핵심을 한 문장으로 적고, 전체 텍스트는 Mermaid 렌더링 없이도 판정 가능해야 한다.
- 전체 ADR 본문과 상세 대안은 사용자가 요청하거나 판정에 필요할 때 제공한다.
- ADR 작성과 사람용 보고서는 reader-first writing 점검을 거쳐 반복적이고 장식적인 AI-slop 신호를 제거한다.

#### 금지

- 별도 Decision premises section, 신뢰도 등급 또는 고정 premise 표를 요구하지 않는다.
- Decision Digest나 semantic diff를 별도 영속 문서 또는 새로운 권위로 저장하지 않는다.
- 요약을 위해 요구사항 값, 허용 집합, 금지 전이, 권한, 필수성, 순서, 유일성, 단위와 실패 보장을 생략하지 않는다.
- 여러 요구사항이나 검증 기준을 하나의 계약 행으로 묶어 일부 누락을 숨기지 않는다.
- 구현 라이브러리, 내부 코드 구조, 튜닝 값과 코드에서 복구 가능한 기본값을 가정으로 올리지 않는다.
- 관찰 가능한 검증 기준에 테스트 파일, 명령, 함수, 클래스, 라이브러리 또는 내부 데이터 표현을 고정하지 않는다.
- 근거가 없는 관계를 다이어그램에 추가하거나 이해에 기여하지 않는 장식용 다이어그램을 만들지 않는다.
- 단순한 단일 ADR PASS에 이해 관계가 없는데 형식을 맞추기 위해 다이어그램을 만들지 않는다.
- 칭찬, 장면 설정, 사용자 요청 반복, 근거 없는 일반론, 미래 추측, 같은 결론·발견·근거의 반복과 내용 없는 heading을 사람용 보고서에 넣지 않는다.
- 반복 대조문, 한 번만 쓰는 장식용 영어 명칭, 강제된 번호 구조와 filler bridge를 논리 구조 대신 사용하지 않는다.
- 표, 다이어그램, blockquote와 강조문으로 인접한 prose를 다시 말하지 않는다.
- 사용자 일화, 프로젝트 결과, 측정값과 인과관계를 사용자 입력이나 저장소 근거 없이 만들지 않는다.
- 코드 경로, 테스트 파일, PR 또는 커밋 계획을 ADR 본문이나 Decision Digest의 계약으로 올리지 않는다.

#### 실패 시 보장

- semantic diff를 확정할 수 없으면 변경 없음으로 표시하지 않고 확인되지 않은 축을 명시한다.
- 중요한 가정이 확인되지 않으면 사실로 기록하지 않고 승인 전 질문으로 남긴다.
- 요약만으로 계약 완전성과 검토 가능성을 보장할 수 없으면 전체 ADR 본문과 재생성 체크로 확장한다.
- Mermaid 관계를 근거로 확인할 수 없으면 관계를 추측하지 않고 텍스트에서 확인되지 않은 축을 명시한다.

#### 관찰 가능한 검증 기준

- 새 ADR이나 변경된 ADR의 requirement contract를 읽으면 각 의무를 다른 의무와 분리해 하나의 구현 리뷰 coverage 행으로 만들 수 있다.
- 각 의무의 관찰 기준만으로 구현 구조와 이름이 다른 두 구현의 계약 준수 여부를 같은 방식으로 판정할 수 있다.
- ADR 본문과 Decision Digest를 검사하면 관찰 기준에 테스트 파일, 명령, 함수, 클래스, 라이브러리와 내부 데이터 표현이 포함되지 않는다.
- 여러 ADR의 충돌이나 의존 관계를 가진 리뷰 fixture는 한눈에 보기와 근거 있는 Mermaid를 생성하고, 같은 내용의 단일 ADR PASS fixture는 불필요한 다이어그램 없이 끝난다.
- 사람용 보고서에서 장식 문장을 제거해도 결론, 계약값, 근거, 영향, 조치와 위험이 그대로 남는다.
- AI-slop 신호가 포함된 ADR fixture를 reader-first pass에 넣으면 결정과 계약을 보존한 채 반복 대조문, 장식용 명칭, 강제 번호 구조, filler bridge와 중복 시각 요소가 제거된다.
- reader-first pass 뒤에도 관찰, 추론과 제안의 근거 수준이 구분되고 확인되지 않은 일화나 결과가 추가되지 않는다.
- 사용자 언어가 명확한 리뷰 fixture는 그 언어를 사용하고, 별도 지시가 없는 fixture는 ADR 본문 또는 리뷰 범위의 주 언어를 사용한다.

### Alternatives

1. **항상 전체 ADR 본문 표시**
   - 장점: 모든 정보가 한 번에 보인다.
   - 단점: 변경되지 않은 내용까지 반복해서 읽어야 한다.

2. **Decision premises를 별도 구조와 신뢰도 등급으로 관리**
   - 장점: 모든 가정이 같은 형식으로 보인다.
   - 단점: Context와 Drivers를 반복하고 작은 ADR에도 추가 분류 비용을 만든다.

3. **영속 ADR은 유지하고 Digest와 선택적 가정 한 줄로 압축**
   - 장점: 권위를 늘리지 않으면서 현재 결정과 중요한 가정에 집중할 수 있다.
   - 단점: 어떤 가정이 결정에 중요한지 모델이 판단해야 한다.

4. **검증 방법을 코드와 테스트에만 맡김**
   - 장점: ADR 본문이 더 짧다.
   - 단점: 코드가 없거나 재생성된 뒤에는 어떤 결과로 계약 충족을 판정해야 하는지 복구하기 어렵다.

## Consequences

### Positive

- 사용자는 ADR의 현재 결정과 계약을 먼저 읽고 필요한 상세만 확장할 수 있다.
- 해당 ADR을 처음 보는 주니어 개발자도 상세 규칙과 경로를 읽기 전에 검토 결과와 다음 조치를 파악할 수 있다.
- 구현 리뷰는 ADR 계약 행을 그대로 요구사항별 달성 화면으로 파생할 수 있다.
- 서로 다른 구현도 같은 관찰 기준으로 계약 준수 여부를 비교할 수 있다.
- 중요한 가정은 기존 ADR 구조 안에서 보이면서 별도 taxonomy를 유지하지 않는다.
- ADR 변경 검토에서 변경되지 않은 문맥을 다시 읽는 비용이 줄어든다.
- ADR이 결정 의도와 중요한 인과관계를 먼저 보여주므로 형식적 목록에서 현재 판단을 복원하는 비용이 줄어든다.
- 관계가 복잡한 리뷰는 Mermaid로 흐름을 외부화하고, 단순 리뷰는 같은 형식 비용을 지불하지 않는다.
- 기존의 single-level read와 current-state 원칙을 유지한다.

### Negative

- 작성자는 어떤 가정이 대안 선택을 바꾸는지 판단해야 한다.
- 작성자는 계약을 독립적인 행과 구현 독립적인 관찰 기준으로 분해해야 한다.
- 보고서 작성자는 다이어그램 트리거와 생략 조건을 판정해야 한다.
- 작성자는 자연스러운 표현과 AI-slop 신호를 문맥에서 구분해야 한다.
- 고정 신뢰도 등급이 없어 가정의 불확실성을 정량 비교할 수 없다.

### Risks

- 간결화를 이유로 계약을 누락할 수 있다. 재생성 체크와 계약 그룹은 원문 값과 규칙을 그대로 유지해야 한다.
- 관찰 기준이 테스트 설계로 내려갈 수 있다. 판정할 외부 결과만 기록하고 실행 수단과 코드 위치는 리뷰 artifact에 둔다.
- 구현 재량을 가정으로 올리면 ADR이 코드 수준으로 내려갈 수 있다. admission gate와 code-readthrough test로 경계를 지킨다.
- 중요한 가정을 생략할 수 있다. 가정이 틀릴 때 adopted alternative가 달라지는지로 포함 여부를 판단한다.
- semantic diff가 문자열 diff로 퇴화할 수 있다. 문장 위치가 아니라 Decision, 계약, Driver와 Consequence의 의미를 기준으로 분류한다.
- 모델이 시각화를 장식으로 남발할 수 있다. 명시된 관계 트리거가 없으면 생략하고, 모든 node와 edge를 ADR 또는 검증 근거에 연결한다.
- 쉬운 설명이 모호한 요약으로 퇴화할 수 있다. 한눈에 보기는 상세 증거를 감추지 않고 결론, 영향, 조치와 위험만 먼저 배치한다.
- reader-first 편집이 중요한 계약을 줄일 수 있다. 문체 수정 뒤 requirement contract와 재생성 체크를 다시 대조한다.
- story와 causal flow가 근거 없는 서사로 변할 수 있다. 사용자 입력과 ADR 근거로 확인된 상황·행동·결과만 사용한다.
- 기술 용어와 고정 label 때문에 리뷰 언어가 과도하게 섞일 수 있다. 사람용 report prose는 선택한 언어를 유지하고 의미가 흐려지는 용어만 원문으로 둔다.
