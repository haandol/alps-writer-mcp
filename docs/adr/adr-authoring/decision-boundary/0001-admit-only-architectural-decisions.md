# ADR 0001: 지속적인 아키텍처 결정만 ADR로 기록

Date: 2026-08-15

## Status

Accepted (2026-08-15)

## Context

ADR 본문에서 파일 경로와 튜닝 값을 제외해도, ADR 생성 조건이 넓으면 구현 선택 자체가 ADR의 핵심 결정으로 올라온다. 라이브러리, SDK, 프레임워크, 자격증명 연결 방식처럼 코드 재작성 과정에서 자유롭게 바뀔 수 있는 선택까지 ADR로 만들면 코드 변경이 ADR 변경을 끌고 간다.

ADR은 코드와 독립적으로 유지할 가치가 있는 결정만 기록해야 한다. 외부 모델과 제공자를 선택하는 결정은 시스템 경계와 비용, 가용성, 규제 조건을 고정할 수 있지만, 같은 경계와 계약을 구현하는 라이브러리와 인증 연결 코드는 그 결정을 실현하는 수단이다.

## Decision Drivers

- 코드 수준 선택이 바뀔 때마다 ADR을 수정하거나 새로 만드는 역방향 의존을 막아야 한다.
- 요구사항 계약과 시스템 경계처럼 재구현 후에도 유지해야 할 결정은 ADR에 남아야 한다.
- 작성, 구현, 동기화, 리뷰 경로가 같은 기준으로 ADR 필요 여부를 판정해야 한다.
- 기술 이름 자체가 아니라 선택이 고정하는 제약과 트레이드오프로 추상화 수준을 판정해야 한다.

## Decision

ADR 작성 전에 **ADR admission gate**를 적용한다. 다음 중 하나를 바꾸는 선택만 ADR 대상으로 인정한다.

- 요구사항 계약, 도메인 불변식, 허용 상태와 전이, 권한과 가시성
- 시스템 경계, 배포 토폴로지, 데이터·키 설계, 보안 신뢰 경계
- 외부 시스템·제공자·모델의 채택과 장애 시 fallback 정책
- 여러 구현을 지속적으로 제약하는 알고리즘, 일관성 모델, 운영 트레이드오프

admission gate를 통과한 뒤에만 requirement gate, code-readthrough test, litmus test를 본문 문장에 적용한다.

### Requirement contract

- 동일한 요구사항 계약, 시스템 경계, 신뢰 경계와 트레이드오프를 유지한 채 다른 선택으로 교체할 수 있는 라이브러리, SDK, 프레임워크, 클래스·모듈 구조, 자격증명 로딩·서명·어댑터 연결 방식은 구현 디테일이다.
- 구현 디테일의 추가·교체·삭제는 ADR을 생성하거나 수정하는 조건이 아니다. 해당 근거와 검증은 코드, 테스트, 프로젝트 규약 문서가 보유한다.
- 기술 제품 이름은 그 선택이 외부 경계나 지속적인 제약을 고정할 때만 ADR에 남는다. 예를 들어 GPT-5.6을 Amazon Bedrock을 통해 사용한다는 선택은 모델·제공자 경계를 고정하므로 ADR 대상이 될 수 있다.
- Bedrock 호출에 특정 SDK를 사용하거나 자격증명을 어떤 provider chain, signer, adapter로 연결하는지는 요구사항이나 보안 신뢰 경계를 별도로 고정하지 않는 한 ADR 대상이 아니다.
- 사용자 인증 방식이나 워크로드 인증 방식이 도메인 계약 또는 보안 신뢰 경계 자체를 바꾸면 ADR 대상이다. 이미 정해진 경계를 구현하는 미들웨어, 라이브러리, credential plumbing은 코드 수준이다.
- 코드에서 ADR에 없는 동작을 발견해도 admission gate를 통과하지 못하면 `Undecided behavior`나 `New ADR needed`로 올리지 않는다.
- 기존 ADR의 핵심 주제가 admission gate를 통과하지 못하면 세부사항을 코드 또는 프로젝트 문서로 내리고 ADR은 폐기 대상으로 제안한다.

### Alternatives

1. **모든 기능·동작 변경을 ADR 대상으로 처리**
   - 장점: 변경 전에 문서가 존재한다.
   - 단점: 구현 선택과 버그 수정까지 ADR이 늘어나고 코드 변경이 ADR 변경을 유발한다.

2. **기술 선택이면 종류와 무관하게 ADR로 기록**
   - 장점: 사용 기술을 한곳에서 찾기 쉽다.
   - 단점: 외부 제공자 선택과 SDK·라이브러리 선택의 지속성 차이를 구분하지 못한다.

3. **admission gate로 지속적인 결정만 기록**
   - 장점: 요구사항과 아키텍처 경계는 보존하면서 구현 재량은 코드에 남는다.
   - 단점: 작성자와 리뷰어가 기술 이름이 아니라 선택이 고정하는 경계와 트레이드오프를 판단해야 한다.

## Consequences

### Positive

- 라이브러리, SDK, credential plumbing 변경이 ADR 생성과 수정을 유발하지 않는다.
- ADR 수와 변경 빈도가 실제 아키텍처 결정 수와 변경 빈도에 가까워진다.
- 외부 제공자, 모델, 신뢰 경계와 fallback처럼 지속적인 선택은 독립적으로 읽을 수 있다.

### Negative

- 같은 기술 주제라도 상황에 따라 ADR 대상 여부가 달라질 수 있다.
- admission gate 판정에는 요구사항과 시스템 경계를 함께 읽는 판단이 필요하다.

### Risks

- 구현 디테일을 제외한다는 이유로 실제 보안 신뢰 경계나 요구사항 계약을 코드 수준으로 내려보낼 수 있다. requirement gate는 admission gate를 통과한 결정 안에서 계속 우선 적용한다.
