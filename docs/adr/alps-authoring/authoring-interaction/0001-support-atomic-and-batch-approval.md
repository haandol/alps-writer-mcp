# ADR 0001: ALPS 작성에 inference-first 추론과 계약 중심 승인을 사용

Date: 2026-08-15

## Status

Accepted (2026-08-22)

## Context

ALPS 작성은 비즈니스 맥락을 구현과 무관한 구체적 제품 계약으로 바꾸는 과정이다. 사용자가
템플릿의 모든 빈칸을 직접 답하면 AI 작성 흐름도 긴 요구사항 인터뷰가 된다. 사용자 입력,
참조 문서, 완료된 Section, 논리적 귀결과 일반적인 도메인 기본값으로 회수 가능한 내용은
AI가 먼저 정리해야 한다.

AI가 추론한 내용을 사용자에게 숨기면 근거 없는 제품 정책이 저장될 수 있다. 특히 금전,
권한, 법률·규제, 개인정보·안전, 되돌리기 어려운 데이터 의미와 외부 약속은 여러 합리적인
선택이 존재할 수 있다. AI는 지배적인 안전한 기본값이 없는 결정만 질문으로 남겨야 한다.

사용자는 저장 전에 요구사항을 확인해야 한다. 전체 원문과 Markdown 표현을 그대로 보여주면
읽기 어렵고 반복 설명과 예시가 중요한 계약을 가린다. 승인 요약은 표현을 줄이되 사용자
입력과 AI가 추론한 제품 상수, 요구사항 값, 권한, 상태, 범위와 성공 조건을 모두 보존해야
한다.

완성된 brief나 기존 문서를 제공한 사용자가 모든 section과 feature를 각각 다시 답하면 이미
명확한 입력에도 반복 비용이 발생한다. Batch 작성은 사용자가 요청한 경우에만 허용하고 승인
단위와 부분 수정 가능성을 유지해야 한다.

## Decision Drivers

- AI는 회수 가능한 비즈니스 변수를 사용자의 반복 답변 없이 제품 상수로 정리해야 한다.
- 질문은 여러 합리적인 선택이 남아 제품 계약이나 관찰 결과가 달라질 때만 사용해야 한다.
- AI가 추론한 제품 상수와 모든 계약 정보는 저장 전에 사용자가 확인할 수 있어야 한다.
- 승인 단위는 Full/Lite Section과 Full Section 7 Feature의 독립 경계를 유지해야 한다.
- 완성된 입력과 batch 요청은 반복 상호작용을 줄이면서 부분 수정과 보류를 허용해야 한다.

## Decision

Full ALPS와 Lite ALPS 작성은 **inference-first**로 동작한다. 작성자는 다음 순서로 비즈니스
변수를 제품 상수로 바꾼다.

1. 사용자가 직접 제공한 정보와 참조 자료를 사용한다.
2. 승인된 이전 Section과 문서 안의 일관된 맥락을 재사용한다.
3. 명시적 계약이 논리적으로 요구하는 결과를 도출한다.
4. 지배적이고 되돌릴 수 있으며 일반적인 도메인 또는 MVP 기본값을 제안한다.

제품 상수는 특정 라이브러리, API, 데이터 구조, 파일이나 함수 이름이 아니다. PoC와 제품이
지켜야 할 구체적인 사용자, 문제, 가치, 범위, 수치, 허용 집합, 권한, 순서, 행동과 관찰
결과다. 일반화는 구현 독립성을 뜻하며, 계약 값을 “적절히”, “충분히”처럼 흐리는 것을
뜻하지 않는다.

작성자는 위 순서로 안전하게 결정할 수 없는 불확실성만 질문한다. 합리적인 선택이 둘 이상이고
그 선택이 사용자 가치, 범위, 금전, 권한, 법률·규제, 개인정보·안전, 되돌리기 어려운 데이터
의미, 외부 약속, 인수 기준 또는 학습 판단을 바꾸면 사용자 결정을 요청한다. 질문이 필요하면
한 개를 기본으로 하며 서로 분리할 수 없는 경우에만 최대 두 개를 함께 묻는다.

ALPS 작성은 저장 전에 **plain-text approval digest**를 대화 응답으로 제시한다. Digest는
Markdown 장식과 전체 원문을 복제하지 않고 목적, 범위, 요구사항 계약, 성공 조건과 미해결
질문을 짧은 레이블과 목록으로 보여준다. 사용자가 직접 제공하지 않은 중요한 제품 상수는
`AI-inferred`로 표시하고 그 근거를 짧게 적는다. 사용자는 이를 승인, 수정 또는 보류할 수
있다.

고정 subsection을 가진 Section은 section 하나가 승인 단위다. 동적 Feature Section은
완전한 vertical slice를 이루는 Feature `7.x` 하나가 승인 단위다. Feature 내부 항목은 함께
검토하며 독립 승인 단위로 쪼개지 않는다.

ALPS 작성은 **atomic mode**를 기본으로 한다. 사용자가 명시적으로 batch를 요청하거나 완성된 구조화 입력을 제공하면 **batch approval mode**를 제공한다. Batch mode도 각 section과 Feature를 독립된 digest로 표시하고 사용자가 전체 승인 또는 항목별 수정과 보류를 선택하게 한다.

승인 후 문서는 subsection별로 저장한다. 고정 Section은 승인된 section에 속한 각 `X.n`을
개별 저장하고, 동적 Feature Section은 승인된 각 Feature `7.x`를 개별 저장한다.

### Requirement contract

- 작성자는 질문하기 전에 사용자 입력, 참조 자료, 승인된 Section, 논리적 귀결과 일반적인
  도메인 기본값을 순서대로 검토한다.
  - 관찰 기준: 해당 정보로 승인 초안을 만들 수 있으면 사용자 질문 없이 완성된 초안을
    제시한다.
- 일반적인 기본값은 지배적이고 되돌릴 수 있으며 이웃 계약과 일관되고 사용자에게 보이는
  제품 정책을 임의로 만들지 않을 때만 사용한다.
  - 관찰 기준: 기본값의 변경이 금전, 권한, 법률·규제, 개인정보·안전, 되돌리기 어려운
    데이터 의미 또는 외부 약속을 바꾸지 않는다.
- 질문은 합리적인 선택이 둘 이상이고 답에 따라 제품 계약이나 관찰 결과가 달라질 때만 한다.
  - 관찰 기준: 각 질문은 답에 따라 달라지는 사용자 가치, 범위, 요구사항, 인수 기준 또는
    학습 판단을 하나 이상 명시할 수 있다.
- 질문이 필요하면 한 개를 기본으로 하고, 서로 분리할 수 없는 경우에만 최대 두 개를 함께
  묻는다.
  - 관찰 기준: 회수 가능한 정보를 확인하기 위한 질문이나 template 채우기용 질문이 없다.
- 제품 상수는 구현 독립적이고 구체적인 값, 허용 집합, 권한, 순서, 범위, 행동 또는 관찰
  결과로 작성한다.
  - 관찰 기준: 구현 기술을 교체해도 계약은 유지되고, 코드를 재작성할 때 같은 제품 동작을
    복원할 수 있다.
- 정확한 요구사항 값이나 규칙을 일반화한다는 이유로 모호하게 만들지 않는다.
  - 관찰 기준: 수치와 단위, 허용 상태, 필수 입력, 권한, 전이, 유일성과 성공 조건이 필요한
    계약에는 정확한 값이 남는다.
- 승인 digest는 Markdown 렌더링에 의존하지 않는 레이블, 짧은 문장과 목록으로 구성한다.
  - 관찰 기준: 원시 text로 읽어도 승인 단위, 핵심 내용과 가능한 응답을 구분할 수 있다.
- 승인 digest는 목적과 사용자 가치, 적용 범위와 제외 범위, 필수 요구사항, 성공 조건과 미해결 질문을 포함한다.
  - 관찰 기준: 사용자는 전체 원문을 읽지 않고도 무엇을 승인하는지 설명할 수 있다.
- 승인 digest는 모든 요구사항 값과 단위, 허용 집합, 필수 입력, 권한과 가시성, 순서와 유일성, 허용·금지 전이와 그 근거를 빠짐없이 포함한다.
  - 관찰 기준: 저장된 요구사항 계약의 각 행을 승인 digest의 항목과 대응시킬 수 있다.
- 사용자가 직접 제공하지 않은 중요한 제품 상수는 `AI-inferred`와 짧은 근거로 표시한다.
  - 관찰 기준: 사용자는 어떤 계약을 AI가 채웠는지 식별하고 승인, 수정 또는 보류할 수 있다.
- 승인 digest는 반복 설명, 예시, Markdown 장식과 구현 세부사항을 생략할 수 있다.
  - 관찰 기준: 생략된 내용이 요구사항 계약, 범위 또는 성공 조건을 추가하거나 변경하지 않는다.
- 저장 내용은 승인 digest에 없던 새 요구사항 계약을 추가하지 않는다.
  - 관찰 기준: 저장된 내용에서 새 계약을 발견하면 승인 누락으로 판정한다.
- AI가 추론한 제품 상수도 사용자 승인 전에는 저장하지 않는다.
  - 관찰 기준: 추론 결과가 approval digest에 없거나 승인되지 않았으면 문서에 나타나지
    않는다.
- 사용자가 전체 내용을 요청하면 해당 승인 단위의 저장 예정 원문을 보여준다.
  - 관찰 기준: 사용자는 승인 전에 요약과 전체 원문 중 필요한 검토 수준을 선택할 수 있다.
- 사용자가 모드를 지정하지 않으면 section별 atomic mode를 사용한다.
  - 관찰 기준: 한 승인 단위가 승인되기 전에 다음 단위를 저장하지 않는다.
- 사용자가 batch 작성을 명시적으로 요청하거나 완성된 구조화 입력을 제공하면 batch approval을 제안할 수 있다.
  - 관찰 기준: 불완전한 입력에는 batch를 임의로 적용하지 않는다.
- Batch 결과는 section과 Feature별 digest를 분리하고 전체 승인, 특정 단위 수정 또는 보류 선택을 제공한다.
  - 관찰 기준: batch 안의 한 단위만 수정하거나 승인하지 않은 채 나머지를 승인할 수 있다.
- 고정 subsection을 가진 Section은 section별로 승인하고 승인된 section의 각 `X.n`
  subsection을 개별 저장한다.
  - 관찰 기준: 하나의 section 승인 뒤 저장 결과에 그 section의 각 subsection이 독립 항목으로 존재한다.
- Section 7은 각 Feature `7.x`를 독립 승인하고 개별 저장한다. `7.x.1`부터 `7.x.6`까지의 내부 항목은 하나의 Feature digest와 저장 내용에 함께 포함한다.
  - 관찰 기준: 승인되지 않은 Feature는 저장되지 않고, 승인된 Feature 하나는 다른 Feature와 합쳐지지 않은 `7.x` 항목으로 존재한다.
- 완료되고 변경되지 않은 승인 단위는 전체 재검토 요청이나 prerequisite 변경이 없으면 다시 승인받지 않는다.
  - 관찰 기준: 재개 시 완료된 단위를 건너뛰고 첫 미완료 단위에서 계속한다.

### Alternatives

1. **모든 빈칸을 사용자에게 질문한다**
   - 장점: AI가 사용자 의도를 잘못 추론할 가능성이 낮다.
   - 단점: 회수 가능한 정보까지 반복 질문해 작성 시간이 길고 사용자 전문성에 품질이
     의존한다.

2. **AI가 질문 없이 문서를 자동 완성한다**
   - 장점: 가장 빠르게 초안을 만든다.
   - 단점: 여러 합리적인 선택이 있는 제품 정책과 요구사항을 사용자 모르게 고정할 수 있다.

3. **Inference-first 초안과 계약 중심 승인**
   - 장점: AI가 회수 가능한 변수를 채우고 사용자는 중요한 불확실성과 추론 계약만 검토한다.
   - 단점: 추론 게이트와 digest 표시가 누락되면 근거 없는 제품 정책이 저장될 수 있다.

## Consequences

### Positive

- 사용자는 회수 가능한 정보를 반복해서 답하지 않고 제품을 바꾸는 결정에 집중한다.
- Full ALPS와 Lite ALPS가 같은 추론·질문·승인 규칙을 사용한다.
- 구현 독립적인 정확한 제품 상수가 PRD에 남는다.
- 사용자는 렌더링 지원과 무관하게 승인 범위를 빠르게 파악한다.
- 요구사항 값과 규칙은 짧은 승인 화면에서도 보존된다.
- Section 7의 Feature 승인과 저장 경계가 일치한다.
- 완성된 brief를 가진 사용자는 반복 확인을 줄인다.
- Batch에서도 저장과 수정 경계가 명확하다.

### Negative

- authoring skill은 도메인 기본값과 사용자 판단이 필요한 정책을 구분해야 한다.
- authoring skill은 저장 내용에서 계약 정보를 추출해 digest와 대조해야 한다.
- 사용자가 전체 문장을 검토하려면 원문 표시를 별도로 요청해야 한다.

### Risks

- 일반 상식을 과도하게 적용하면 사용자 의도와 다른 제품 정책을 제안할 수 있다. 보호된
  표면과 다중 유효 선택은 질문 게이트로 남기고 모든 중요한 추론은 digest에 표시한다.
- 질문 게이트를 과도하게 적용하면 inference-first 흐름이 다시 긴 인터뷰가 될 수 있다.
  질문마다 답에 따라 달라지는 계약이나 관찰 결과를 설명할 수 있어야 한다.
- 요약 과정에서 요구사항 값이나 규칙을 누락할 수 있다. 정적 prompt 테스트와 shipping prompt 행동 시나리오가 계약 완전성을 검증한다.
- 불완전한 입력을 batch로 오인할 수 있다. 불명확하면 atomic mode를 사용한다.
- Feature 내부 항목을 독립 저장 단위로 오인하면 불완전한 vertical slice가 완료 상태가 될 수 있다. Section 7의 승인과 저장 단위는 Feature `7.x`로 고정한다.
