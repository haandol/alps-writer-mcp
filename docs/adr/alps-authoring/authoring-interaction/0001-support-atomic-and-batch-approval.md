# ADR 0001: ALPS 작성에 대화형 컨텍스트 보완과 계약 중심 승인을 사용

Date: 2026-08-15

## Status

Accepted (2026-08-23)

## Context

ALPS 작성은 사용자가 이미 가진 제품 맥락과 AI가 묻는 질문을 결합해 구현과 무관한 구체적
제품 계약을 만드는 대화 과정이다. 사용자가 템플릿의 모든 빈칸을 한 번에 준비할 필요는
없다. AI는 현재 Section에 부족한 맥락을 찾아 한 번에 소수의 질문으로 보완하고, 답변을
기존 대화와 승인된 Section에 통합해야 한다.

반대로 AI가 질문 없이 완성 초안을 먼저 만들도록 강제하면, 사용자는 문서 작성 과정에서
자신의 맥락을 설명하고 수정할 기회를 잃는다. 질문을 금지하거나 정해진 출력 레이블과
문장형식을 요구하는 평가도 대화를 자연스럽게 이어가기보다 평가 문구를 맞추는 방향으로
작성자를 유도한다.

사용자는 저장 전에 자신이 승인하는 요구사항을 확인해야 한다. 전체 원문을 매번 반복하면
읽기 어렵고, 지나치게 짧은 요약은 값, 권한, 상태, 범위와 성공 조건을 숨길 수 있다.
승인 digest는 표현을 줄이되 구현 결과를 바꾸는 계약은 모두 보존해야 한다.

완성된 brief나 기존 문서를 제공한 사용자는 여러 Section을 한 번에 검토할 수 있어야 한다.
Batch 작성도 Section과 Feature의 독립 승인 경계를 유지하고 부분 수정과 보류를 허용해야
한다.

## Decision Drivers

- AI는 사용자가 부족한 제품 맥락을 대화 중에 점진적으로 설명하게 하며 이미 제공되거나
  승인된 정보는 반복 질문하지 않아야 한다.
- Lite는 Lite 도입 직전 Full의 질문, 제안, 승인 방식을 따라야 하며 공통화를 이유로 Full의
  스킬, 가이드, 질문 순서와 예시를 재설계하지 않아야 한다.
- Lite의 AI 제안값은 별도 추론 출처 표시 없이 사용자가 값 자체를 검토하고 승인할 수 있어야
  한다.
- 승인 화면은 구현 결과를 바꾸는 요구사항과 규칙을 빠짐없이 보여주고 Section과 Feature의
  독립 승인 경계를 유지해야 한다.
- 행동 평가는 제품 계약과 안전 경계를 검증하되 자연어 표현을 불필요하게 고정하지 않아야
  한다.

## Decision

Lite ALPS는 Lite 도입 직전 Full ALPS의 **대화형 작성 방식**을 그대로 사용한다. 공통화의
방향은 Lite가 Full을 따르는 방향이며, Full을 새 공통 규칙에 맞춰 바꾸는 방향이 아니다.
Full의 스킬, Section 가이드, overview와 Full 템플릿 작성 규칙은 그 기준 동작을 유지한다.

1. 작성자는 사용자 메시지, 참조 자료, 승인된 이전 Section과 현재 문서 맥락을 먼저 읽는다.
2. 현재 작성 단위에 필요한 정보 중 이미 회수 가능한 내용은 다시 묻지 않는다.
3. 부족하거나 서로 다른 해석이 가능한 맥락은 한 번에 한 개의 집중 질문으로 묻고, 밀접하게
   연결돼 분리할 수 없을 때만 최대 두 개를 함께 묻는다.
4. AI는 답변을 기다리는 동안 후보 값이나 초안을 자연스럽게 제안할 수 있다. Lite는 제안을
   사용자 입력과 같은 계약 형식으로 표시하며 별도 추론 출처 레이블을 붙이지 않는다.
5. 현재 작성 단위에 필요한 맥락이 이미 충분하면 불필요한 질문을 추가하지 않고 승인
   digest를 제시할 수 있다. 이것은 질문을 금지하는 규칙이 아니라 완료된 맥락을 반복 확인하지
   않는 규칙이다.
6. 금전, 권한, 법률·규제, 개인정보·안전, 되돌리기 어려운 데이터 의미, 외부 약속, 인수
   기준과 같이 여러 선택이 제품 계약을 바꾸는 결정은 사용자 답변으로 확정한다.

Section 가이드의 질문은 사용자가 답해야 할 고정 인터뷰 목록이나 작성자가 건너뛰어야 할
추출 체크리스트가 아니다. 현재 맥락에서 어떤 정보가 부족한지 판단하는 대화 가이드다.
작성자는 질문의 순서와 표현을 사용자 답변에 맞게 조정한다.

ALPS 작성은 저장 전에 **plain-text approval digest**를 대화 응답으로 제시한다. Digest는
Markdown 장식과 전체 원문을 복제하지 않고 목적, 범위, 요구사항 계약, 성공 조건과 미해결
질문을 짧은 레이블과 목록으로 보여준다. 사용자는 값과 규칙 자체를 읽고 승인, 수정 또는
보류한다.

행동 평가와 정적 prompt 검사는 계약상 필요한 의미와 안전 경계를 검증한다. 특정 사용자
노출 문구, 작성 출처 레이블, 장식 형식, 문장 순서 또는 질문의 정확한 표현은 그 자체가 제품
계약인 경우가 아니면 통과 조건으로 고정하지 않는다. 금지 검사는 사용자 승인 없는 저장,
명시적 범위 위반, 계약값 누락처럼 실제로 잘못된 결과를 허용하는 경우에만 사용한다.

고정 subsection을 가진 Section은 Section 하나가 승인 단위다. 동적 Feature Section은
완전한 vertical slice를 이루는 Feature `7.x` 하나가 승인 단위다. Feature 내부 항목은 함께
검토하며 독립 승인 단위로 쪼개지 않는다.

ALPS 작성은 **atomic mode**를 기본으로 한다. 사용자가 명시적으로 batch를 요청하거나 완성된
구조화 입력을 제공하면 **batch approval mode**를 제공한다. Batch mode도 각 Section과
Feature를 독립된 digest로 표시하고 사용자가 전체 승인 또는 항목별 수정과 보류를 선택하게
한다.

승인 후 문서는 subsection별로 저장한다. 고정 Section은 승인된 Section에 속한 각 `X.n`을
개별 저장하고, 동적 Feature Section은 승인된 각 Feature `7.x`를 개별 저장한다.

### Requirement contract

- 작성자는 현재 작성 단위의 질문 전에 사용자 입력, 참조 자료, 승인된 Section과 문서 맥락을
  검토한다.
  - 관찰 기준: 이미 답한 정보를 그대로 다시 요구하는 질문이 없다.
- 현재 작성 단위에 부족한 맥락이 있으면 한 번에 한 개의 집중 질문을 사용하고, 분리할 수
  없는 경우에만 최대 두 개를 함께 묻는다.
  - 관찰 기준: 사용자는 한 응답에서 무엇을 결정하거나 설명해야 하는지 알 수 있다.
- 필요한 맥락이 이미 충분하면 질문을 만들기 위해 질문하지 않고 승인 초안을 제시할 수 있다.
  - 관찰 기준: 완성된 입력에는 반복 확인 질문이 필수로 추가되지 않는다.
- 가이드 질문은 고정 인터뷰 스크립트나 질문 금지 체크리스트가 아니라 현재 맥락의 누락을
  찾는 대화 가이드로 사용한다.
  - 관찰 기준: 사용자의 답변에 따라 질문 순서, 표현과 생략 항목이 달라질 수 있다.
- AI는 후보 값과 초안을 제안할 수 있으며, 사용자는 대화 중 이를 승인, 수정 또는 거절할 수
  있다.
  - 관찰 기준: 제안값이 질문을 막지 않고 사용자의 후속 설명으로 변경될 수 있다.
- Full의 스킬, 9개 Section 가이드, overview와 Full Section 템플릿 작성 규칙은 Lite 도입
  직전의 대화형 작성 동작을 유지한다.
  - 관찰 기준: Lite 정렬을 위해 Full의 질문 우선순위, 예시, wizard 또는 승인 흐름을
    변경하지 않는다.
- Lite 승인 digest와 저장 문서는 추론 여부를 나타내는 별도 출처 레이블을 사용하지 않는다.
  - 관찰 기준: Lite에서 사용자 입력과 AI 제안값이 동일한 계약 형식으로 표시된다.
- 여러 유효한 답이 금전, 권한, 법률·규제, 개인정보·안전, 되돌리기 어려운 데이터 의미,
  외부 약속 또는 인수 기준을 바꾸면 사용자 답변으로 확정한다.
  - 관찰 기준: 작성자가 보호된 제품 정책을 기본값만으로 확정하지 않는다.
- 제품 상수는 구현 독립적이고 구체적인 값, 허용 집합, 권한, 순서, 범위, 행동 또는 관찰
  결과로 작성한다.
  - 관찰 기준: 구현 기술을 교체해도 계약은 유지된다.
- 정확한 요구사항 값이나 규칙을 일반화한다는 이유로 모호하게 만들지 않는다.
  - 관찰 기준: 수치와 단위, 허용 상태, 필수 입력, 권한, 전이, 유일성과 성공 조건이 필요한
    계약에는 정확한 값이 남는다.
- 승인 digest는 Markdown 렌더링에 의존하지 않는 레이블, 짧은 문장과 목록으로 구성한다.
  - 관찰 기준: 원시 text로 읽어도 승인 단위, 핵심 내용과 가능한 응답을 구분할 수 있다.
- 승인 digest는 목적과 사용자 가치, 적용 범위와 제외 범위, 필수 요구사항, 모든 계약값과
  규칙, 성공 조건과 미해결 질문을 포함한다.
  - 관찰 기준: 저장된 요구사항 계약의 각 행을 승인 digest의 항목과 대응시킬 수 있다.
- 행동 평가는 제품 계약과 안전에 필요한 의미를 검증하고, 계약이 아닌 사용자 노출 문구,
  장식, 문장 순서와 정확한 질문 표현을 통과 조건으로 요구하지 않는다.
  - 관찰 기준: 같은 의미를 자연스럽게 표현한 유효한 응답이 표현 차이만으로 실패하지 않는다.
- 저장 내용은 승인 digest에 없던 새 요구사항 계약을 추가하지 않는다.
  - 관찰 기준: 저장된 내용에서 새 계약을 발견하면 승인 누락으로 판정한다.
- AI가 제안한 제품 상수도 사용자 승인 전에는 저장하지 않는다.
  - 관찰 기준: 제안 결과가 approval digest에 없거나 승인되지 않았으면 문서에 나타나지
    않는다.
- 사용자가 전체 내용을 요청하면 해당 승인 단위의 저장 예정 원문을 보여준다.
  - 관찰 기준: 사용자는 승인 전에 요약과 전체 원문 중 필요한 검토 수준을 선택할 수 있다.
- 사용자가 모드를 지정하지 않으면 Section별 atomic mode를 사용한다.
  - 관찰 기준: 한 승인 단위가 승인되기 전에 다음 단위를 저장하지 않는다.
- 사용자가 batch 작성을 명시적으로 요청하거나 완성된 구조화 입력을 제공하면 batch
  approval을 사용할 수 있다.
  - 관찰 기준: 불완전한 입력에는 batch를 임의로 적용하지 않는다.
- Batch 결과는 Section과 Feature별 digest를 분리하고 전체 승인, 특정 단위 수정 또는 보류
  선택을 제공한다.
  - 관찰 기준: batch 안의 한 단위만 수정하거나 승인하지 않은 채 나머지를 승인할 수 있다.
- 고정 subsection을 가진 Section은 Section별로 승인하고 승인된 Section의 각 `X.n`
  subsection을 개별 저장한다.
  - 관찰 기준: 하나의 Section 승인 뒤 각 subsection이 독립 항목으로 존재한다.
- Section 7은 각 Feature `7.x`를 독립 승인하고 개별 저장한다. `7.x.1`부터 `7.x.6`까지의
  내부 항목은 하나의 Feature digest와 저장 내용에 함께 포함한다.
  - 관찰 기준: 승인되지 않은 Feature는 저장되지 않고 승인된 Feature끼리 합쳐지지 않는다.
- 완료되고 변경되지 않은 승인 단위는 전체 재검토 요청이나 prerequisite 변경이 없으면 다시
  승인받지 않는다.
  - 관찰 기준: 재개 시 완료된 단위를 건너뛰고 첫 미완료 단위에서 계속한다.

### Alternatives

1. **모든 빈칸을 고정 순서로 질문한다**
   - 장점: 사용자가 모든 값을 직접 제공한다.
   - 단점: 이미 답한 정보까지 반복하는 긴 템플릿 인터뷰가 된다.

2. **질문 없이 완성 초안을 먼저 생성한다**
   - 장점: 빠르게 문서 형태를 볼 수 있다.
   - 단점: 사용자가 맥락을 설명하는 대화를 약화하고 AI가 제품 정책을 과도하게 결정할 수
     있다.

3. **대화형 컨텍스트 보완과 계약 중심 승인**
   - 장점: AI가 기존 맥락을 활용하면서 부족한 부분만 질문하고 사용자는 값과 규칙을
     점진적으로 확정한다.
   - 단점: 작성자는 회수 가능한 정보와 추가 질문이 필요한 정보를 구분해야 한다.

## Consequences

### Positive

- 사용자는 완성된 기획 입력을 미리 준비하지 않고 AI와 대화하며 제품 맥락을 채울 수 있다.
- 이미 제공된 정보는 재사용하면서도 부족한 맥락을 질문으로 보완한다.
- Lite가 기존 Full과 같은 작성 경험을 제공한다.
- Full 작성 방식은 Lite 공통화의 영향 없이 유지된다.
- AI 제안은 대화를 돕지만 사용자 승인 전에는 제품 계약이 되지 않는다.
- 요구사항 값과 규칙은 짧은 승인 화면에서도 보존된다.
- 행동 평가가 자연어 스타일보다 실제 계약 위반을 찾는 데 집중한다.
- Section 7의 Feature 승인과 저장 경계가 일치한다.
- Batch에서도 저장과 수정 경계가 명확하다.

### Negative

- 대화 횟수는 질문 없는 자동 초안보다 늘어날 수 있다.
- 작성자는 현재 맥락에 맞는 다음 질문을 선택해야 한다.
- 행동 평가는 표현 일치 대신 의미 판정을 해야 하므로 scorer 설계가 더 신중해야 한다.

### Risks

- 질문을 과도하게 사용하면 다시 긴 템플릿 인터뷰가 될 수 있다. 이미 제공된 정보는 반복하지
  않는다.
- 질문을 너무 적게 사용하면 AI가 제품 정책을 임의로 채울 수 있다. 보호된 결정과 여러 유효
  선택은 사용자에게 묻는다.
- 요약 과정에서 요구사항 값이나 규칙을 누락할 수 있다. 승인 digest의 계약 완전성을
  검증한다.
- 출력 검사를 지나치게 느슨하게 만들면 실제 범위 위반을 놓칠 수 있다. 승인 없는 저장,
  계약값 누락과 명시적 금지 위반은 계속 검증한다.
- 불완전한 입력을 batch로 오인할 수 있다. 불명확하면 atomic mode를 사용한다.
