# ADR 0001: ALPS 작성에 계약 중심 승인 요약과 atomic/batch 승인을 사용

Date: 2026-08-15

## Status

Accepted (2026-08-18)

## Context

질문에 답하며 PRD를 만드는 사용자는 저장 전에 요구사항을 확인해야 한다. 전체 원문과 Markdown 표현을 그대로 보여주면 렌더링을 보장할 수 없는 대화 환경에서 읽기 어렵고, 반복 설명과 예시가 중요한 계약을 가린다.

승인 화면을 짧게 만들더라도 요구사항 값, 권한, 상태, 범위와 성공 조건을 숨기면 사용자가 보지 못한 계약이 저장될 수 있다. 승인 요약은 표현을 줄이되 구현 결과를 바꾸는 정보를 모두 보존해야 한다.

완성된 brief나 기존 문서를 제공한 사용자가 모든 section과 feature를 각각 다시 승인하면 이미 명확한 입력에도 반복 비용이 발생한다. Batch 작성은 사용자가 요청한 경우에만 허용하고 승인 단위와 부분 수정 가능성을 유지해야 한다.

## Decision Drivers

- 사용자는 Markdown 렌더링 없이도 승인 정보를 빠르게 읽을 수 있어야 한다.
- 승인 화면은 구현 결과를 바꾸는 요구사항과 규칙을 빠짐없이 보여줘야 한다.
- 기본 대화형 사용자는 작성 중 누락을 section 또는 feature별로 확인할 수 있어야 한다.
- 완성된 입력을 제공한 사용자는 반복 승인 없이 진행할 수 있어야 한다.
- Batch 승인에서도 각 section과 Feature의 경계를 유지하고 일부 항목만 수정하거나 보류할 수 있어야 한다.

## Decision

ALPS 작성은 저장 전에 **plain-text approval digest**를 대화 응답으로 제시한다. Digest는 Markdown 장식과 전체 원문을 복제하지 않고 목적, 범위, 요구사항 계약, 성공 조건과 미해결 질문을 짧은 레이블과 목록으로 보여준다.

Sections 1-6과 8-9는 section 하나가 승인 단위다. Section 7은 완전한 vertical slice를 이루는 Feature `7.x` 하나가 승인 단위다. Feature 내부 항목은 함께 검토하며 독립 승인 단위로 쪼개지 않는다.

ALPS 작성은 **atomic mode**를 기본으로 한다. 사용자가 명시적으로 batch를 요청하거나 완성된 구조화 입력을 제공하면 **batch approval mode**를 제공한다. Batch mode도 각 section과 Feature를 독립된 digest로 표시하고 사용자가 전체 승인 또는 항목별 수정과 보류를 선택하게 한다.

승인 후 문서는 subsection별로 저장한다. Sections 1-6과 8-9는 승인된 section에 속한 각 `X.n`을 개별 저장하고, Section 7은 승인된 각 Feature `7.x`를 개별 저장한다.

### Requirement contract

- 승인 digest는 Markdown 렌더링에 의존하지 않는 레이블, 짧은 문장과 목록으로 구성한다.
  - 관찰 기준: 원시 text로 읽어도 승인 단위, 핵심 내용과 가능한 응답을 구분할 수 있다.
- 승인 digest는 목적과 사용자 가치, 적용 범위와 제외 범위, 필수 요구사항, 성공 조건과 미해결 질문을 포함한다.
  - 관찰 기준: 사용자는 전체 원문을 읽지 않고도 무엇을 승인하는지 설명할 수 있다.
- 승인 digest는 모든 요구사항 값과 단위, 허용 집합, 필수 입력, 권한과 가시성, 순서와 유일성, 허용·금지 전이와 그 근거를 빠짐없이 포함한다.
  - 관찰 기준: 저장된 요구사항 계약의 각 행을 승인 digest의 항목과 대응시킬 수 있다.
- 승인 digest는 반복 설명, 예시, Markdown 장식과 구현 세부사항을 생략할 수 있다.
  - 관찰 기준: 생략된 내용이 요구사항 계약, 범위 또는 성공 조건을 추가하거나 변경하지 않는다.
- 저장 내용은 승인 digest에 없던 새 요구사항 계약을 추가하지 않는다.
  - 관찰 기준: 저장된 내용에서 새 계약을 발견하면 승인 누락으로 판정한다.
- 사용자가 전체 내용을 요청하면 해당 승인 단위의 저장 예정 원문을 보여준다.
  - 관찰 기준: 사용자는 승인 전에 요약과 전체 원문 중 필요한 검토 수준을 선택할 수 있다.
- 사용자가 모드를 지정하지 않으면 section별 atomic mode를 사용한다.
  - 관찰 기준: 한 승인 단위가 승인되기 전에 다음 단위를 저장하지 않는다.
- 사용자가 batch 작성을 명시적으로 요청하거나 완성된 구조화 입력을 제공하면 batch approval을 제안할 수 있다.
  - 관찰 기준: 불완전한 입력에는 batch를 임의로 적용하지 않는다.
- Batch 결과는 section과 Feature별 digest를 분리하고 전체 승인, 특정 단위 수정 또는 보류 선택을 제공한다.
  - 관찰 기준: batch 안의 한 단위만 수정하거나 승인하지 않은 채 나머지를 승인할 수 있다.
- Sections 1-6과 8-9는 section별로 승인하고 승인된 section의 각 `X.n` subsection을 개별 저장한다.
  - 관찰 기준: 하나의 section 승인 뒤 저장 결과에 그 section의 각 subsection이 독립 항목으로 존재한다.
- Section 7은 각 Feature `7.x`를 독립 승인하고 개별 저장한다. `7.x.1`부터 `7.x.6`까지의 내부 항목은 하나의 Feature digest와 저장 내용에 함께 포함한다.
  - 관찰 기준: 승인되지 않은 Feature는 저장되지 않고, 승인된 Feature 하나는 다른 Feature와 합쳐지지 않은 `7.x` 항목으로 존재한다.
- 완료되고 변경되지 않은 승인 단위는 전체 재검토 요청이나 prerequisite 변경이 없으면 다시 승인받지 않는다.
  - 관찰 기준: 재개 시 완료된 단위를 건너뛰고 첫 미완료 단위에서 계속한다.

### Alternatives

1. **전체 원문을 Markdown으로 표시**
   - 장점: 저장 예정 문장을 모두 볼 수 있다.
   - 단점: 렌더링이 없는 환경에서 구조가 약하고 반복 설명이 핵심 계약을 가린다.

2. **계약 완전성 규칙 없는 짧은 요약**
   - 장점: 가장 빠르게 읽을 수 있다.
   - 단점: 요약에서 빠진 요구사항이 사용자 확인 없이 저장될 수 있다.

3. **계약 중심 plain-text digest와 기본 atomic, 명시적 batch opt-in**
   - 장점: 중요한 계약을 보존하면서 읽기 비용과 반복 승인을 줄인다.
   - 단점: digest와 저장 내용 사이의 계약 일치를 prompt와 행동 평가에서 검증해야 한다.

## Consequences

### Positive

- 사용자는 렌더링 지원과 무관하게 승인 범위를 빠르게 파악한다.
- 요구사항 값과 규칙은 짧은 승인 화면에서도 보존된다.
- Section 7의 Feature 승인과 저장 경계가 일치한다.
- 완성된 brief를 가진 사용자는 반복 확인을 줄인다.
- Batch에서도 저장과 수정 경계가 명확하다.

### Negative

- authoring skill은 저장 내용에서 계약 정보를 추출해 digest와 대조해야 한다.
- 사용자가 전체 문장을 검토하려면 원문 표시를 별도로 요청해야 한다.

### Risks

- 요약 과정에서 요구사항 값이나 규칙을 누락할 수 있다. 정적 prompt 테스트와 shipping prompt 행동 시나리오가 계약 완전성을 검증한다.
- 불완전한 입력을 batch로 오인할 수 있다. 불명확하면 atomic mode를 사용한다.
- Feature 내부 항목을 독립 저장 단위로 오인하면 불완전한 vertical slice가 완료 상태가 될 수 있다. Section 7의 승인과 저장 단위는 Feature `7.x`로 고정한다.
